# Personal social profiles

The personal social page is separate from Signal Relay. A visitor can link a Twitch, X, Reddit or TikTok profile or YouTube channel without Discord using a signed, private browser profile; alternatively, a Discord-signed-in member can link one to their Discord account. Provider authorization is explicit and uses a real OAuth authorization-code exchange. Browser-profile links remain private and are separate from Discord profiles; signing in later does not merge them. No manual URL is accepted as a verified provider link. Facebook and Instagram are explicitly unsupported, not connected or verified: Meta's Instagram API targets professional accounts, and a reliable general-purpose personal Facebook profile URL and required permissions have not been verified for this use. Providers are unconfigured until the operator supplies credentials; X, Reddit and TikTok additionally require explicit operator enablement after any required approval and cost review. These are verification snapshots, not ongoing API connections or private feeds; names can become stale, so reconnect to refresh them. YouTube verification requires the read-only YouTube account scope and exactly one channel returned for the selected Google identity; no channel or an ambiguous multi-channel response fails closed.

Profiles are private by default. Discord-signed-in members can separately share or hide a connected profile for any Discord server they belong to; browser-profile connections have no server-sharing controls. Use **Reconnect** on an existing profile to refresh it without disconnecting first; it is available when the provider is configured and enabled. Disconnect deletes the profile, all its visibility choices and pending connections for that provider. A different provider identity also resets all sharing; reconnecting the same identity preserves choices. Leaving a server suppresses display while membership cannot be verified but does not erase the choice; rejoining restores it unless the member turns it off or disconnects. Existing grants for unlisted or former servers are shown by ID and can be individually removed even when Discord membership lookup fails.

Each connection and sharing decision rotates a per-user, per-provider revision, including revocations of already-private servers. Enabling sharing atomically requires the revision and provider identity observed by the user; stale enables fail and the page refreshes its choices. Changes for one server may therefore require a refresh before enabling another server for the same provider. Existing accounts receive a revision during database bootstrap; all processes sharing the database must run the updated code before enabling this feature, as older code cannot enforce revisions.

The web directory checks the viewer's current Discord guild membership and independently checks the profile owner's membership using an unexpired dashboard session and the Discord API. Failures are hidden rather than disclosed; owners may need to sign in again. After membership checks finish, the page rechecks all sharing revisions together; profiles changed during the request are omitted. Each page checks up to 20 shared records; use Load more even if a page has no eligible profiles. Discord's guild-list endpoint currently returns at most the first 200 servers, so other servers cannot be selected or verified here. As with any network response, a revocation cannot recall data already sent to a viewer.

The Discord `/social` command shows channel-permission-filtered server alerts in ephemeral replies and links to the official personal-social page, where Discord sign-in independently identifies the viewer. The link carries the server ID and, for supported providers, the selected platform as navigation hints; it carries no user ID or profile data and does not grant access. The directory rechecks membership and sharing, and its pagination cursors are bound to the server and platform. Personal profiles are not returned in Discord. `/social` rejects `RUN_NATIVE_COMMAND` automation, because synthetic delivery cannot guarantee privacy for alerts. The personal-profile bridge is hard-disabled even if bridge environment variables are set: the bot and dashboard share a Unix UID and credential access, allowing another process to impersonate users and retrieve private profiles. Enabling it requires a separately designed and verified isolation boundary; a shared secret, loopback or an environment switch is not sufficient. No live Discord/bridge test was performed.

One possible future identity model is direct Discord HTTP interactions: verify Discord's Ed25519 signature on the exact raw body and timestamp, enforce freshness and durable one-time interaction IDs, derive user and server only from the verified payload, and deliver results only through Discord's ephemeral interaction response. This requires an actual Discord interaction endpoint and routing design, not gateway events or caller-supplied IDs. It also requires isolating the social database, session tokens and provider secrets from other processes, plus a review of response races, replay and deployment controls. This is a design direction, not an enabled feature or a substitute for that isolation.

## Operator setup

Register a confidential [Twitch developer application](https://dev.twitch.tv/docs/authentication/register-app/) and add exactly `https://YOUR-DASHBOARD-ORIGIN/api/personal-social/twitch/callback` as its OAuth redirect. Set `SOCIAL_TWITCH_CLIENT_ID` and `SOCIAL_TWITCH_CLIENT_SECRET` in the dashboard's private environment, and configure the existing `DISCORD_REDIRECT_URI` with the same canonical dashboard origin. HTTPS is required in production. Do not commit credentials. Twitch may impose registration or approval requirements. The callback and session must use the same host; separate dashboard/site deployments have separate databases unless explicitly configured to share the existing `prisma/dashboard.db`, so connections and sessions do not automatically follow between deployments.

The public site's personal-social link and Discord login are routed to this canonical host before setting OAuth state. The reverse proxy must preserve the browser's public `Host` header; otherwise the canonical login may redirect repeatedly. A relative return path such as `/gaming` stays on the canonical dashboard host. The session cookie remains host-only: login does not authenticate a separate root-domain deployment or copy its session/database. Supporting a signed-in root-domain page would require a separately designed secure cross-host session architecture; no shared-domain cookie is introduced here.

For YouTube, enable the YouTube Data API in a Google Cloud project, configure its OAuth consent screen and a web OAuth client with `https://YOUR-DASHBOARD-ORIGIN/api/personal-social/youtube/callback`, then set `SOCIAL_YOUTUBE_CLIENT_ID` and `SOCIAL_YOUTUBE_CLIENT_SECRET`. Google may require consent-screen verification and test-user enrollment for the sensitive read-only scope. Use a dedicated Google OAuth project: revocation may revoke the entire grant for that project. Do not use shared credentials that power other features.

For X, create a confidential OAuth 2.0 web app with callback `https://YOUR-DASHBOARD-ORIGIN/api/personal-social/x/callback`. Set `SOCIAL_X_CLIENT_ID` and `SOCIAL_X_CLIENT_SECRET`. Only after checking X API access and potential charges, explicitly set `SOCIAL_X_ENABLED=true`. X requires `tweet.read` and `users.read` for `/2/users/me`; these permissions can include protected posts and profiles even though this feature fetches only the authenticated profile.

For Reddit, request the necessary developer/API access and register a confidential web app with callback `https://YOUR-DASHBOARD-ORIGIN/api/personal-social/reddit/callback`. Set `SOCIAL_REDDIT_CLIENT_ID`, `SOCIAL_REDDIT_CLIENT_SECRET` and a descriptive ASCII `SOCIAL_REDDIT_USER_AGENT` identifying your application and contact, then explicitly set `SOCIAL_REDDIT_ENABLED=true` only after review/approval. The requested scope is `identity`, with temporary access.

For TikTok, register an HTTPS web callback `https://YOUR-DASHBOARD-ORIGIN/api/personal-social/tiktok/callback`, request approval for `user.info.basic` and `user.info.profile`, and set `SOCIAL_TIKTOK_CLIENT_ID` to the TikTok client key and `SOCIAL_TIKTOK_CLIENT_SECRET` to the client secret. Set `SOCIAL_TIKTOK_ENABLED=true` only after approval. If the user withholds either scope or the provider does not supply a valid TikTok profile URL, linking fails closed. TikTok issues a refresh token; this feature never stores it and attempts to revoke the access authorization after verification.

At startup the existing dashboard SQLite bootstrap creates additive tables. No provider access or refresh tokens are saved. Tokens are used only to fetch the authenticated profile and a best-effort revocation is attempted; on failure, authorization may remain valid until the provider expires or revokes it. Users can also remove the application's authorization in their provider settings. OAuth state is random, provider- and identity-bound, expires after ten minutes and is claimed once; starting a new connection cancels older pending attempts for that provider, and completion and disconnection are atomically ordered. YouTube and X also use PKCE. State-changing endpoints require the canonical same-origin `Origin` header and either a valid Discord session or the signed browser-profile cookie. Clearing that browser cookie means that browser profile cannot be recovered or merged into a Discord account.

Before enabling publicly, test with consenting accounts and registered provider apps: sign in with Discord, link each provider, confirm private-by-default, share to one server, check another member and a nonmember, turn sharing off, reconnect a different identity, disconnect, and test Discord expiry/unavailability. No real-account test has been performed by this implementation. Existing Discord OAuth sessions and database backups follow the dashboard's existing security and retention practices.
