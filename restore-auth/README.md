# Isolated restore authorization broker (not enabled)

This is a standalone Discord OAuth authorization service, not a restore service. It signs an actor, guild, action and SHA-256 hash of the exact request bytes for two minutes. It must run under a separate, exclusive OS identity, with its private signing key and OAuth secret unavailable to the dashboard, bot and other services. The existing dashboard session cannot provide that boundary. Existing restore HTTP gates remain disabled.

Supported proof actions are dashboard-settings restore, feature-settings restore, Undo Setup, Pokémon dashboard access, and panel repair. Each proof authorizes only the exact request bytes, expires after two minutes, and can be used once.

The sample systemd unit is **not installed**. Before any activation, operators must provision and review all of the following without copying the current shared dashboard secret:

1. A separate HTTPS origin, routed by a trusted reverse proxy directly to `/run/possum-restore-auth/broker.sock`, never through the existing dashboard. Reject unexpected hosts, do not log callback query strings, cookies, proofs, request bodies or authorization headers, and protect proxy configuration from the dashboard UID. The broker rejects POSTs from other origins and uses host-only secure cookies.
2. A Discord OAuth application/redirect registration for `https://<isolated-origin>/oauth/callback`, with `identify guilds`. Store its client secret and a newly generated Ed25519 PEM private key as root-owned, mode-0600 systemd credential sources. Keep the corresponding public key in a root-owned, non-writable location for each verifier. Never expose the private key to the shared UID.
3. Root-owned, non-writable broker code and `/etc/possum/restore-auth.conf` containing `RESTORE_AUTH_ORIGIN=https://<isolated-origin>` and `DISCORD_CLIENT_ID=<id>`. The example unit uses a dynamic UID and grants only the reverse proxy's `www-data` group access to the Unix socket. Adapt and verify the proxy identity, systemd version, socket permissions, filesystem ownership, and process isolation before use.
4. Each restore service uses its verifier with `proof.cjs`, the root-owned public key and a durable **atomic** one-use `jti` store inaccessible to untrusted services. `loadTrustedPublicKey` checks root ownership and permissions throughout the key path. `createReplayStore` requires an existing owner-only directory and creates each record exclusively; on storage errors it fails closed. Bind the proof to the authenticated actor, guild, action, and exact original HTTP body bytes, including mode and preview or confirmation token; independently require the guild and action in the body to match the proof. Validate all settings semantically and check the current state; consume the proof before mutation. Protect verifier code, state and ingress with distinct OS identities/ACLs; a shared UID can otherwise change code, tokens, replay state or data directly. Never trust a dashboard-supplied actor or forwarded identity without the signed proof. The bot now has a fail-closed verifier for the supported actions; it is not enabled until the broker and verifier paths are provisioned on the VPS.
5. Add a trusted user-facing integration that sends the exact reviewed JSON bytes without reserialization. Reauthentication on this separate origin is intentional. The broker's small review form is for manual authorization; it does not submit a restore. Existing setup writers must also be authorized, isolated and coordinated. Migrate sessions and data only with a reviewed preservation/rollback procedure, and deploy all writers together.

The broker stores OAuth tokens and login state only in memory and loses sessions on restart. Replay records accumulate; an operator must arrange safe cleanup only after expiry and all verifier clock-skew margins. The signed proof is not a full backup, a preview, or proof that a restore succeeded. Discord must be reachable for every authorization. This configuration has not been installed or validated on the VM.
